# 实施计划

设计依据为 `references/Quark-VFS-Implementation-Draft-v0.1.md`。先完成 M0 的兼容性核查，再按已验证能力推进 M1。

## 已完成切片：M0 诊断与协议基础

1. 核查官方来源、版本、独立 CLI 支持约定和状态目录行为，记录可复核证据。
2. 建立 Python 工程、配置解析和结构化诊断入口。默认只检查本地状态，显式探测时调用官方环境识别命令。
3. 实现受控子进程和协议解析，分别处理环境识别纯文本、NDJSON 与完整 Artifact；用合成样例测试错误和边界。
4. 独立审查实现，修复发现的问题，运行测试及包装层安装与本地命令行烟雾验收。
5. 根据证据列出需要官方授权或真实网盘验证的剩余 M0 项目。

这一切片的完成条件是：诊断工具可安装运行；未配置、配置不安全、协议损坏和能力未验证时给出明确结果；测试不访问真实网盘，不保存凭证。

截至 2026-10-13，本地基础、真实 Codex 环境识别、浏览器授权和账号探活已完成。受限文档往返样例也已通过，包括成功源上传后的 checkpoint 恢复、产物往返，以及移动到测试回收目录后再次下载校验。详细证据见 `VERIFICATION.md`；后续 M0 专项与 M1 当前状态见下方交付任务。

## 里程碑

- 首个真实使用验收采用用户选定的文档工作流：下载资料、在本地处理、上传产物。
- M0 实测：确认官方运行时安装和实际授权，使用专用测试目录验证枚举、身份、碰撞、逐项结果、下载关联与恢复。
- M1：共用文件核心、受控 CLI、任务持久化、回收恢复和薄 skill，按能力门禁逐项开放。
- M2：真实 Codex 启动链验证通过后接入 stdio MCP。
- M3：按实际需要增加文本读取、复制或可恢复替换。

代码实现和真实服务验收分别记账。合成样例通过不改变上游能力门禁；云端操作结果未知时先核对再恢复。

## M0 能力审计与 M1 交付

1. 在独占测试目录补测超过 100 项的完整枚举、搜索、重命名、撞名、部分成功、下载记录关联、恢复与短文件覆盖。每项记录通过、失败或不能确认的原因；失败能力保持关闭，测试对象不永久删除。
2. 冻结共用核心与官方适配器的接口，实现账号作用域、完整目录快照与本地分页、路径解析、有限 stat、文件操作和逐项持久化任务。真实账号 ID 无法从公开状态命令取得时，使用明确的本地作用域及不可变云标记验证绑定，不用昵称冒充身份。
3. 实现回收清单、恢复事件与数据库遗失后的重建：先验证远端恢复清单可读，再移动对象；恢复默认拒绝覆盖，未知结果先核对。
4. 将 CLI 和薄 skill 接入同一核心，保留可读的能力限制。MCP、本期未验收的原子替换和文件内断点续传保持关闭。
5. 由独立代理交叉审查，主代理运行本地完整检查及专用目录中的 M1 真实验收，更新能力矩阵、恢复说明与验收证据。

实现分工为官方适配与 M0 验收、目录/传输/操作/任务核心、回收恢复与 CLI 三条独立写入路线。初始 64 项回归作为基线；新行为通过注入的测试适配器验证，并与真实网盘验收分别记账。
